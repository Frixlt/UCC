# ADR-02: Архитектура демона uccd — Concurrency, Tokio Actors и Hardware Access

## Статус
Принято (Accepted)

## Контекст
Демон `uccd` решает одновременно несколько задач:
1. Обслуживание 122 D-Bus методов и 7 сигналов интерфейса `de.uniwill.uccd`.
2. Высокочастотный сбор телеметрии (CPU температуры, частоты, мощности, dGPU/iGPU, обороты вентиляторов) каждые 1–2 секунды.
3. Низкоуровневое управление железом через `/dev/tuxedo_io` ioctl и `/sys`.
4. BLE-коммуникация с внешней помпой/кулером LCT через BlueZ GATT.
5. Применение профилей питания при смене источника (AC, Type-C, Battery).

Конкурентная запись в `/dev/tuxedo_io` или одновременная смена частот и TDP из разных потоков в C++ исторически приводила к взаимным блокировкам или race conditions.

## Решение
1. **Tokio Runtime & Actor Model**:
   - Демон `uccd` строится на базе `tokio` (single multi-threaded runtime).
   - Аппаратные ресурсы, требующие эксклюзивного доступа (`/dev/tuxedo_io`), инкапсулируются в отдельный **Hardware Controller Actor**, принимающий команды через `tokio::sync::mpsc` очередь.
   - Это гарантирует **Single-Writer** модель: никакие два потока не могут одновременно вызывать ioctl к EC/Uniwill/Clevo.
2. **Сбор телеметрии**:
   - Мониторинг CPU и sysfs выполняется в отдельной циклической задаче с неблокирующим чтением sysfs файлов.
   - Актуальные значения телеметрии публикуются в разделяемое состояние (`Arc<RwLock<TelemetrySnapshot>>` / lockless atomics), откуда D-Bus методы читают их без ожидания аппаратных шин.
3. **BLE Water Cooler**:
   - BLE-компонент работает как независимый actor с генерационными тайм-аутами, keepalive проверками (10 секунд, порог 3) и жестким интервалом между записями (`BLE_WRITE_GAP >= 80 ms`).
4. **Безотказность и fail-closed**:
   - Все ошибки ioctl, BlueZ и sysfs логируются через `tracing`, не приводя к панике (zero `unwrap` в production-коде).
   - При сбое опроса сенсоров вентиляторы переводятся в аппаратный авто-режим (`W_UW_FANAUTO`), предотвращая перегрев.

## Последствия
- Полная изоляция критических секций работы с оборудованием.
- Время отклика D-Bus методов снижается до долей миллисекунды, так как D-Bus читает закэшированный snapshot телеметрии вместо блокирующего I/O.
