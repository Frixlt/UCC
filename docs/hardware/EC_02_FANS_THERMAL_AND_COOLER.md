# Clean-Room технический анализ протоколов EC Uniwill: управление вентиляторами, датчики и жидкостное охлаждение (СЖО)

Настоящий документ представляет собой clean-room спецификацию регистров встроенного контроллера (EC), битовых масок, кодировок и протокольных последовательностей платформ Uniwill (включая шасси проекта `0x1A` / `IDY_7Y` — MECHREVO YAOSHI `X6AR55xY` и проект `0x10` — MAIBENBEN Tsunami `X629`), составленную по четырём независимым источникам: [MechControl-RE](https://github.com/Liddo-kun/MechControl-RE/blob/main/docs/architecture.md), [open-uniwill-cc](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), официальному драйверу ядра Linux [uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c) и локальному репозиторию `UCC-rust-migration`.

Все адреса указаны в 16-битном адресном пространстве EC RAM, доступном через методы ACPI `ECRR`/`ECRW` (устройство `INOU0000`, Linux `/dev/uwcc`, Windows OEM IOCTL `0x9C40A488`/`0x9C40A48C`) или WMI `AcpiTest_MULong.GetSetULong` ([open-uniwill-cc: Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)).

## 1. Таблицы кривых вентиляторов в EC RAM: RamFan 1.5, RamFan 2 и CCI

### 1.1 Определение поддержки и побайтовая карта RamFan 1.5 (`0x0F00..0x0F5F`)

Поддержка таблиц вентиляторов в EC RAM (RamFan 1.5) объявляется битом `BIT(6)` (`0x40`) регистра `0x078E` (`EC_ADDR_FAN_CTRL` / `UNIVERSAL_FAN_CTRL`) ([Linux kernel: uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c), [open-uniwill-cc: regs.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/regs.py)).

Область RamFan 1.5 занимает ровно **96 байт** (`0x0F00..0x0F5F`): по 3 массива на 16 уровней (индексы `0..15`) для CPU и GPU.

### 1.2 Индексация, маркер `Duty[0] = 0`, гистерезис и правила заполнения (padding)

1. **Сдвиг индексов `UpT` и `DownT`:**
   - При чтении таблицы уровня `i ∈ [0..15]`: `UpT_level[0] = 0`, `UpT_level[i] = EC[UP_BASE + i - 1]` для `i ≥ 1`; `DownT_level[i] = EC[DOWN_BASE + i + 1]` для `i < 15` (и `EC[DOWN_BASE + 15]` для `i = 15`); `Duty_level[i] = EC[DUTY_BASE + i] / 2` ([open-uniwill-cc: fan.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/fan.py)).
   - При записи таблицы: для `i ∈ [0..15]` в `UP_BASE + i` пишется `UpT_level[i + 1]` (при `i = 15` всегда `0xFF`), в `DOWN_BASE + i + 1` (только при `i < 15`) пишется `DownT_level[i]`, а в `DUTY_BASE + i` пишется `Duty_level[i] × 2` (или `0xFF`, если `Duty_level[i] > 100`) ([open-uniwill-cc: fan.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/fan.py)).
2. **Обязательный маркер `Duty[0] = 0`:**
   - В спецификации `MechControl-RE` байт `Duty[0]` (`0x0F20` для CPU и `0x0F50` для GPU) **обязательно записывается как `0x00`** независимо от пользовательской кривой — EC использует его как маркер нулевого уровня. Для активных уровней `i ≥ 1` значение округляется до чётного с нижним порогом `2` (`1 %`): `max(2, (raw_duty / 2) * 2)` ([MechControl-RE: src/ec.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec.cpp)).
3. **Правила гистерезиса (`DownT`):**
   - В `MechControl-RE` массив `DownT` пересчитывается детерминированно при каждой записи (не полагаясь на сохранённые значения), причём `DownT[0]` никогда не перезаписывается ([MechControl-RE: src/ec.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec.cpp)):
     - Для `1 ≤ i < active`: `DownT[i] = max(0, UpT[i - 1] - 4)` (°C, гистерезис 4 °C).
     - Для `i = active` (если `active < 16`): `DownT[active] = min(255, (active > 1 ? max(0, UpT[active - 2] - 4) : 0) + 4)`.
     - Для `active < i < 16`: `DownT[i] = 0xFF`.
   - В `open-uniwill-cc` пороги `DownT` допускаются произвольными, но монотонно неубывающими (равные температуры допустимы, так как встречаются в заводских таблицах), а наивысший активный уровень при более чем одной точке обязан иметь скважность не ниже `40 %` (`raw ≥ 80`) ([open-uniwill-cc: fan.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/fan.py)).
4. **Заполнение неиспользуемых слотов (padding) и системы без dGPU:**
   - **Модель `open-uniwill-cc`**: уровень считается неиспользуемым, если `Duty > 100 %` (`0xFF`) или (при `i > 0`) `UpT ∈ {0, 255}`. Всё после первого неиспользуемого уровня нормализуется в `0xFF` (`UpT = DownT = Duty = 0xFF`), так как часть EC заполняет хвост нулями вместо `0xFF` ([open-uniwill-cc: fan.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/fan.py)).
   - **Модель `MechControl-RE`**: неактивные слоты `UpT[active..15]` и `DownT[active+1..15]` заполняются `0xFF` (`paddingTemp = 255`), а неактивные слоты `Duty[active..15]` повторяют последнее активное значение `last = max(2, (duty.back() / 2) * 2)` (при типовых 10 активных точках из 16 в `IDY_7Y.json`, где `paddingDuty = 200`) ([MechControl-RE: IDY_7Y.json](https://github.com/Liddo-kun/MechControl-RE/blob/main/Profiles/MECHREVO/IDY_7Y.json), [MechControl-RE: src/ec.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec.cpp)).
   - **Отсутствие dGPU**: если дискретный GPU отсутствует, `0x07C5 BIT(7)` сбрасывается в `0`, а в область GPU (`0x0F30..0x0F5F`) всё равно дублируется кривая CPU — некоторые прошивки EC (например, XMG EVO EC 2.16) читают строки GPU для общего расчёта и второго вентилятора на нижнем уровне ([MechControl-RE: src/ec.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec.cpp)).

### 1.3 Безопасная последовательность записи пользовательской кривой

1. Сбросить защёлку таблицы: `0x07C6` `BIT(2) = 0` (строго masked RMW, маска `0x04`).
2. Задать режим раздельных кривых: `0x07C5` `BIT(7) = 1` (если кривые CPU/GPU раздельные и есть dGPU) или `0` (если общая кривая) — masked RMW, маска `0x80`.
3. Записать 96 байт таблицы в `0x0F00..0x0F5F`.
4. Проверить, что таблица валидна (`EC[0x0F00] != 0 || EC[0x0F01] != 0`), и взвести защёлку `0x07C6` `BIT(2) = 1` (masked RMW, маска `0x04`) ([open-uniwill-cc: Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [open-uniwill-cc: fan.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/fan.py), [MechControl-RE: src/ec.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec.cpp)).

### 1.4 Рукопожатие (`0x0F5D..0x0F5F`) для загрузки заводских таблиц EC

Последние три байта `GPU Duty` используются для запроса выгрузки встроенной (заводской) таблицы из ROM EC в область `0x0F00..0x0F5F` ([open-uniwill-cc: Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [open-uniwill-cc: fan.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/fan.py), [open-uniwill-cc: hwoc.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/hwoc.py)):

1. Для чтения базовых (воздушных) таблиц временно сбросить `0x0741` `BIT(0)` (`AP_EXIST = 0`) и восстановить после завершения ([open-uniwill-cc: fan.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/fan.py)).
2. Записать код запрашиваемой таблицы в `0x0F5F`:
   - **Стандартные (воздушные) таблицы**: `1` — Turbo, `2` — Gaming, `3` — Office ([open-uniwill-cc: regs.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/regs.py), [open-uniwill-cc: fan.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/fan.py)).
   - **Таблицы для СЖО (Liquid Cooling)**: `5` — Turbo (LC), `6` — Gaming (LC) / Custom (LC), `7` — Office (LC) ([open-uniwill-cc: hwoc.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/hwoc.py), [open-uniwill-cc: Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)).
3. Записать маркер рукопожатия: `0x0F5D = 0xFD`, `0x0F5E = 0xC9`.
4. Опрашивать `0x0F5D` и `0x0F5E` до 10 раз с шагом `0,5 с` (таймаут `5 с`), пока EC не перезапишет оба байта значениями, отличными от `(0xFD, 0xC9)`. После этого в `0x0F00..0x0F5F` размещена запрошенная заводская таблица ([open-uniwill-cc: fan.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/fan.py), [open-uniwill-cc: hwoc.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/hwoc.py)).

### Требование tear-free чтения 16-битных тахометров

Поскольку 16-битное значение оборотов считывается через два раздельных 8-битных обращения к EC (`ECRR`), обновление счётчика прошивкой между чтением MSB и LSB (например, переход `0x06FF → 0x0700`) порождает артефакт разрыва (tearing) вида `0x0600` или `0x07FF` (±255 RPM). Даже `regmap_bulk_read(..., 2)` в [uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c) поверх байтового `regmap` выполняет два последовательных чтения. Корректный tear-free протокол при байтовом доступе:

1. Прочитать `hi1 = read(MSB)`.
2. Прочитать `lo = read(LSB)`.
3. Повторно прочитать `hi2 = read(MSB)`.
4. Если `hi1 == hi2`, вернуть `(hi1 << 8) | lo`; иначе повторить (до 3 попыток, при неисправимом расхождении вернуть последнее согласованное чтение или ошибку).

### 4.2 Протокол переключения EC на таблицы вентиляторов СЖО (`LiquidHWOC`)

1. **Условия входа:** подтверждены `0x07A4 BIT(7) == 1` и `0x07C8 BIT(5) == 1`, СЖО подключена по BLE (установлен `0x07C7 BIT(1) = 1`), датчик потока стабильно подтверждает циркуляцию охлаждающей жидкости не менее `5,0 с`, доступен драйверный интерфейс для вызова `PWUP` ([open-uniwill-cc: hwoc.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/hwoc.py)).
2. **Блокировка пользовательских таблиц:** управляющая служба прекращает запись пользовательских таблиц в `0x0F00..0x0F5F` (`blocked = True`).
3. **Загрузка LC-таблицы EC:** для активного режима выполняется рукопожатие `0x0F5F = {Office: 7, Gaming: 6, Turbo: 5, Custom: 6}`, затем `0x0F5D = 0xFD`, `0x0F5E = 0xC9`, и ожидание перезаписи `0x0F5D`/`0x0F5E` со стороны EC (до 10 × 0,5 с). На примере Tsunami загружаемая таблица СЖО содержит 3 активных ступени (`55 °C → 30 %`, `66 °C → 40 %`, `75 °C → 55 %`) ([open-uniwill-cc: hwoc.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/hwoc.py), [open-uniwill-cc: Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)).
4. **Синхронизация `PWUP`:** служба читает `level = (EC[0x07C7] >> 2) & 0x07` и вызывает `INOU0000.PWUP(level)` немедленно, а также повторно при каждом получении WMI-события `0xC2`.
5. **Выход (отключение СЖО или пропадание потока):** служба снимает `0x07C7 BIT(1)`, разблокирует пользовательские таблицы, заново применяет таблицу текущего режима и повторно синхронизирует `PWUP` ([open-uniwill-cc: hwoc.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/hwoc.py)).

| **Отсутствие протокола записи и проверки состояния** | `apply_curve` не сбрасывает `0x07C6 BIT(2)` перед записью, не выставляет `0x07C5 BIT(7)` и проверяет активность через `ec_read(0x0F00) & 0x03 == 0x03`. | Последовательность: `0x07C6 BIT(2) = 0` (RMW) → `0x07C5 BIT(7)` (RMW) → запись 96 байт → проверка валидности → `0x07C6 BIT(2) = 1` (RMW). Активность проверяется по `(ec_read(0x07C6) & 0x04) != 0`. | Гонка чтения таблицы прошивкой во время частичной перезаписи и ложное определение активного состояния. |
