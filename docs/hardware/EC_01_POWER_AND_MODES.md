# Clean-Room технический анализ регистров питания, GPU и режимов работы Uniwill EC

Настоящий документ представляет собой clean-room спецификацию аппаратных регистров встроенного контроллера (EC), битовых масок, формул кодирования, протокольных последовательностей и ACPI-методов платформ Uniwill (включая шасси проекта `0x1A` / MECHREVO YAOSHI X6AR55xY и `0x10` / MAIBENBEN Tsunami X629). Спецификация составлена по результатам сверки трёх открытых источников и сопоставлена с текущей реализацией в локальном репозитории `UCC-rust-migration` (`crates/ucc-hardware/src/uwcc/mod.rs` и `kernel/uwcc-rs/src/validation.rs`).

### 1.2 Критическое предупреждение по `0x0727` (`CUME` и `BIT(7)` `PL4D` / `pl4_doubled`)

Регистр `0x0727` требует особой осторожности из-за двойной роли его старших битов и расхождения трактовки `BIT(7)` в источниках:
- **`BIT(6)` (`0x40`, `CUME`)**: на платах проекта `0x1A` (MECHREVO Yaoshi, Aurora X, XMG NEO 16 E25) DSDT объявляет именованное поле `CUME` в области `ECMG` по смещению `0x0727`, бит 6 ([acpifields.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/acpifields.py)). Без одновременной установки `0x0726 BIT(7)` и `0x0727 BIT(6)` встроенный контроллер игнорирует пользовательские лимиты `PL1`/`PL2`/`PL4` и удерживает заводские кривые вентиляторов ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)).
- **`BIT(7)` (`0x80`) — расхождение интерпретации, единое правило безопасности**:
  - В [Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md) `0x0727 BIT(7)` документирован как поле DSDT `PL4D` («отключение PL4»), которое служба управления не имеет права изменять.
  - В [profiles.h](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.h) и [ec_session.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec_session.cpp) `0x0727 BIT(7)` считывается **до активации EC** как аппаратный индикатор удвоенного масштаба регистра PL4 (`pl4_doubled`: при `BIT(7) == 1` цена младшего разряда `0x0785`, `0x0732`, `0x0736`, `0x07A9` и `SMRW[2]` равна `2 Вт/LSB`).
  - Оба источника сходятся в строгом инварианте: **`BIT(7)` регистра `0x0727` никогда нельзя модифицировать**; любая запись `CUME` должна выполняться строго через RMW с маской `0x40`.

### 1.3 Полная последовательность активации EC и рукопожатие `0x0741 BIT(2)`

По данным [controller.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/controller.cpp) и [architecture.md](https://github.com/Liddo-kun/MechControl-RE/blob/main/docs/architecture.md), полноценная активация EC выполняется в 7 последовательных шагов с паузой **150 мс** между шагами:

1. Инициализация контура OC: записать `0x0709 = 0x05`, затем `0x0708 = 0x01`.
2. Запрос активации и рукопожатия:
   - На моделях с поддержкой подтверждения (`activationAck = true`, включая `IDY_7Y` / `0x1A`): записать `0x0741 = 0x05` (`BIT(0) | BIT(2)`).
   - На моделях без подтверждения (например, `GMxZGxx`, где EC использует `BIT(2)` иначе): RMW `0x0741` с `val = 0x01`, `mask = 0x05`.
3. Активация световой полосы: записать `0x0748 = 0x81` (`LIGHTBAR_APP_EXISTS | LIGHTBAR_WELCOME`), после чего при необходимости восстановить сохранённое состояние подсветки.
4. Включение пользовательского контура питания: RMW `0x0726` (`val = 0x80, mask = 0x80`), затем RMW `0x0727` (`val = 0x40, mask = 0x40`).
5. Отключение NVIDIA Whisper Mode: RMW `0x07C5` (`val = 0x40, mask = 0x60`); если `(read(0x07C6) & 0x03) != 0`, очистить биты `1..0` в `0x07C6` (`val = 0x00, mask = 0x03`).
6. Синхронизация флага СЖО: записать `0x07C7 = 0x0E` (если СЖО подключена) либо `0x07C7 = 0x0C` (без СЖО).
7. Фиксация режима Custom: записать `0x0706 = 0x41`.
8. Опционально (для платформ с `operatingMode = true`, стартующих в Office): RMW `0x0751` с маской `0xB0` — записать `0x10` (Turbo), если `0x049F BIT(1) == 1`, иначе `0x00` (Gaming).
9. **Ожидание ACK-рукопожатия**: опрашивать `0x0741` до **31 раза** с интервалом **100 мс** (максимум ~3 с). Условие успеха:
   - при `activationAck = true`: `(read(0x0741) & 0x05) == 0x01` (`BIT(0)` удержан, `BIT(2)` сброшен прошивкой EC);
   - при `activationAck = false`: `(read(0x0741) & 0x01) == 0x01`.
10. **Восстановление после сна / сброса EC**: если в процессе работы `read(0x0741) & 0x01 == 0`, активация считается потерянной; требуется сбросить `ecBypass` (если был активен), повторно выполнить шаги 1–9 и заново применить пользовательские лимиты и кривые вентиляторов ([controller.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/controller.cpp)).
11. **Деактивация при завершении работы**: сбросить `0x0741 BIT(0)` (`ENABLE_MANUAL_CTRL`), чтобы вернуть аппаратной кнопке режима автономное переключение в EC ([uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c)).

### 1.4 Приоритет режимов DSDT `PMSC` и ловушки `0x0751` / `0x0752` / `0x0753` / `0x0754`

Метод прошивки DSDT `PMSC` вычисляет активный режим в строгом порядке приоритета ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)):

1. **`CUME == 1`** (`0x0727 BIT(6)`) → **Custom** (наивысший приоритет).
2. Иначе **`TBME == 1`** (`0x0751 BIT(4)`) → **Turbo**.
3. Иначе **`UFME == 1`** (`0x0751 BIT(7)`) → **Office** (на `0x1A` жёстко ограничивает CPU ~45 Вт).
4. Иначе → **Gaming**.

Критические особенности и ловушки:
- **Ловушка «одиночного `CUME`» на `0x1A` (Aurora X / Yaoshi)**: при установке `CUME = 1` без `UFME` прошивка EC на части пользовательских кривых вентиляторов через ~45 секунд плавно разгоняет оба вентилятора до 100% независимо от температуры. Поскольку `PMSC` проверяет `CUME` раньше `UFME`, установка связки **`CUME` (`0x0727 BIT(6)`) + `UFME` (`0x0751 = 0x80`, либо `0xC0` с FanBoost) + `0x07C6 BIT(2)`** удерживает систему в Custom и обеспечивает корректную работу любой кривой ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)).
- **Обратная ловушка (`UFME` без `CUME`)**: запись `0x0751 BIT(7)` при `CUME == 0` переводит `0x1A` в режим Office с потолком 45 Вт.
- **Ловушка регистров `0x0752`, `0x0753`, `0x0754`**: на шасси `0x1A` (X6AR55xY) регистр `0x0752` **не является** индексом профиля `1..=3`, а регистры `0x0753` и `0x0754` являются **лимитом тока VRM процессора и максимальным током VRM (в амперах)**, а не флагом `MODE_ENABLE` ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [ec_session.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec_session.cpp), [profiles.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.cpp)). Запись `0` или `1` в `0x0753` на `0x1A` искажает аппаратный токовый лимит VRM.

### 2.2 Опасный режим обхода адаптивных лимитов `ecBypass` (`0x0780` / `0x0781`)

Регистры `0x0780` (`ecBypass`) и `0x0781` (`ecBypassLimits`) реализуют бенчмарк-обход адаптивного снижения PL1/PL2/PL4 со стороны EC ([IDY_7Y.json](https://github.com/Liddo-kun/MechControl-RE/blob/main/Profiles/MECHREVO/IDY_7Y.json), [architecture.md](https://github.com/Liddo-kun/MechControl-RE/blob/main/docs/architecture.md), [controller.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/controller.cpp), [Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)):

- **Ограничение по прошивке**: верифицировано исключительно для проверенных версий EC (на IDY_7Y — строго версия `77.0`, читаемая из `0x0454` [major] и `0x047D` [minor]), магическое значение активации `0x0780 = 0xA2`.
- **Обязательные предусловия перед записью**:
  1. Подключён блок питания: `read(0x0490) & 0x01 == 1`.
  2. EC находится в нормальном рабочем состоянии: `read(0x06E6) == 1`.
  3. Исходное состояние регистров чистое: `read(0x0781) == 0` и `read(0x0780) == 0`.
  4. Активен пользовательский контур CPU: `(read(0x0741) & 0x01) != 0` и `(read(0x0727) & 0x40) != 0`.
- **Побочные эффекты и риски**:
  - EC перестаёт применять внутренние адаптивные ограничения CPU (новые лимиты стабилизируются за ~24 с), **принудительно выводит вентиляторы на 100%** и изменяет выходы тепловой защиты.
  - **Критическая опасность зависания EC**: при выходе EC из нормального состояния (`0x06E6 != 1` — сон, отключение экрана, пропадание БП) установленный `0x0780 = 0xA2` приводит к **зависанию контроллера**.
  - **Политика безопасности**: никогда не сохранять в профилях, блокировать автоматический сон на время работы, немедленно сбрасывать `0x0780 = 0x00` при отключении питания, переходе в сон, срабатывании тепловой защиты, реинициализации EC, выходе из программы или обнаружении остаточного значения на старте; пока сброс не подтверждён обратным чтением `0x00`, блокировать все прочие записи в EC.

### 3.2 Определение наличия дискретной GPU с EC-управлением питанием

Согласно [profiles.h](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.h):
- На современных прошивках ID модуля GPU хранится в `0x07D2` (`GPU_MODULE_ID`). Если `0x07D2 == 0xFF` или чтение не удалось — наличие неизвестно.
- На более старых прошивках `0x07D2 == 0`, а наличие GPU индицируется `0x0456 BIT(7)` (`SYSTEM_ID`). На таких прошивках EC-управление питанием GPU допустимо только при наличии валидного `DefaultTGP` в таблице `SMRW` (на устаревших платах адреса `0x0743..0x0747` использовались под ручную кривую вентиляторов).

### 3.3 ACPI-методы устройства `INOU0000` (`SMRW`, `PWUP`, `PWBT`, `PWDB`) и взаимодействие с NVIDIA `NPCF`

#### Метод `SMRW` (Smart APC Table)
- **Вызов**: `\_SB.INOU.SMRW(Buffer(N){ 0xBB, key, 0x00, ... })` (в Windows OEM-драйвере — IOCTL `0x9C40A500`, `input = 0xBB | (key << 8)`) ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [ec.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/ec.py), [ec.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec.cpp)).
- **Критическая особенность длины буфера (`AE_AML_BUFFER_LIMIT`)**: на платах проекта `0x1A` (в частности MECHREVO Yaoshi X6AR55xY, issue #5 в open-uniwill-cc) метод `SMRW` в DSDT безусловно создаёт поле записи `WRBF` (биты `8..103`, т.е. до 13-го байта аргумента `Arg0`) даже при чтении (`0xBB`). Передача 4-байтового буфера вызывает исключение ACPICA `AE_AML_BUFFER_LIMIT` до выполнения тела метода. Необходимо передавать буфер с нулевым дополнением длиной не менее 16 байт (в [uwcc.c](https://github.com/aspidovss/open-uniwill-cc/blob/main/kernel/uwcc.c) выполняется автоподбор по последовательности `16 → 32 → 64 → 4` байт; в локальном `acpi_shim.c` передаётся 64-байтовый буфер).
- **Карта 12-байтовой таблицы `INOU0000` (`key = 0..11`)** ([ec.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/ec.py), [ec_session.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec_session.cpp), [profiles.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.cpp)):

| Индекс (`key`) | Поле `SMAPCTABLE` | Единицы и семантика | Замечания по декодированию |
|---|---|---|---|
| `0` | `PL1` | Макс. PL1, Вт | Валидно при `15..253` (ограничивается аппаратным `power_max`). |
| `1` | `PL2` | Макс. PL2, Вт | Валидно при `15..253`. |
| `2` | `PL4` | Макс. PL4 (raw) | При `0x0727 BIT(7) == 1` умножать на 2 (`raw * 2 Вт`); валидно при `15..250`. |
| `3` | `TccOffset` | Мин. смещение TCC или макс. °C | `<= 40` → Intel `inverted_offset` (`max = 105 - raw`); `80..120` → AMD `direct` (`max = raw`). |
| `4` | **`ConfigurableTGP`** | **Макс. добавочный cTGP сверх базового, Вт** | Верхняя граница TGP без DB = `data[7] + data[4]`. (`0` = cTGP фиксирован на базовом уровне). |
| `5` | `DynamicBoost` | Макс. Dynamic Boost, Вт | Обычно `0..25 Вт` (валидно `<= 50`). Полный лимит GPU = `data[7] + data[4] + data[5]`. |
| `6` | `TargetTemperature` | Целевая температура GPU, °C | Например, `87 °C`. |
| `7` | **`DefaultTGP`** | **Базовый (минимальный) TGP, Вт** | Базовая точка отсчёта для смещения в `0x0744` и `0x0788` (например, `95 Вт` на IDY_7Y, `150 Вт` на Tsunami). |
| `8` | `DynamicBoostCpuTdp` | CPU TDP при Dynamic Boost, Вт | Может быть `0` или `0xFF`. |
| `9..11` | Служебный хвост / маркер | В `INOU0000` DSDT при чтении DWord с шагом 4 байта — `0xFF 0xFF 0xFF 0xFF` в байтах `8..11`; в Windows OEM-драйвере (`spec(9)`) эхо `0xBB` подтверждает валидность ответа. | Зависит от того, возвращается ли пакет по 1 ключу или DWord по байтовому смещению `REOF`. |

- **Отличие от legacy-формата**: в локальном `mod.rs` поддерживается запасной 20-байтовый формат из пяти пар little-endian `u16` `(min, max)` для `(PL1, PL2, PL4, cTGP, DynamicBoost)`, который используется только при неуспешном декодировании нативной 12-байтовой таблицы `INOU0000`.

#### Метод `PWUP(level)` и взаимодействие с NVIDIA `NPCF`
- **Сигнатура**: `\_SB.INOU.PWUP(level)` — принимает 3-битное целое `level & 0x07` (`0..=7`); в Windows OEM-драйвере вызывается через IOCTL `0x9C40A504` (с опечаткой в OEM-имени `"PUWP"`) ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [uwcc.c](https://github.com/aspidovss/open-uniwill-cc/blob/main/kernel/uwcc.c)).
- **Механика**: при подключённой СЖО EC вычисляет целевой уровень мощности OC и публикует его в `0x07C7 BIT(4..2)` (отправляя WMI-событие `0xC2` `EV_HWOC`). Сам регистр `0x07C7 BIT(4..2)` недоступен для записи — чтобы уровень вступил в силу, хост обязан вызвать `PWUP(level)`. Метод `PWUP` уведомляет ACPI-устройство NVIDIA `NPCF` и dGPU о новом бюджете питания ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), локальный `kernel/uwcc-rs/src/acpi_shim.c`).
- **Реальные уровни на оборудовании**: замеры на Tsunami (`0x10`) подтверждают уровни **4 и 5** (`level = 0` → лимит GPU `150 Вт`, `level = 4` или `5` → лимит GPU `175 Вт`, прирост частоты +13–15%) ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)).

#### Методы `PWBT` и `PWDB` (локальный `uwcc-rs`)
- В `open-uniwill-cc`, `MechControl-RE` и `uniwill-acpi.c` прямые вызовы ACPI `PWBT` и `PWDB` не применяются: управление cTGP и Dynamic Boost идёт через EC-регистры `0x0743..0x0746`, из которых EC/BIOS пробрасывает параметры в `NPCF` (плюс `PWUP` для СЖО).
- В локальном `kernel/uwcc-rs/src/acpi_shim.c` дополнительно вызываются методы `\_SB.INOU.PWBT(value)` (Base TGP, предел валидации `<= 300`) и `\_SB.INOU.PWDB(value)` (Dynamic Boost, предел `<= 100`) для явного уведомления NVIDIA `NPCF`. При их совместном использовании с EC-регистрами необходимо строго разделять единицы: `0x0744` принимает **смещение** (`target_W - base_TGP_W`), тогда как `PWBT` принимает значение в соответствии со спецификацией DSDT конкретной платы (абсолютный Base TGP или смещение — требуется проверка по DSDT перед передачей одного и того же `raw` в оба интерфейса).
