# Clean-Room технический анализ идентификации шасси Uniwill, маппинга ProjectID и аудит allowlist `UCC-Revorked`

Данный отчёт выполнен по принципу **clean-room**: из внешних источников извлечены исключительно адреса аппаратных регистров EC RAM, битовые маски, кодировки величин, последовательности переходов состояний и спецификации протоколов (без копирования исходного кода).

---

## 1. Регистры идентификации, возможностей и состояния шасси Uniwill

Все адреса ниже относятся к 16-битному адресному пространству EC RAM, доступному через ACPI-методы `ECRR`/`ECRW` устройства `INOU0000` (OEM-драйвер или `/dev/uwcc`) либо через WMI-мост `AcpiTest_MULong.GetSetULong` ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c)).

### 1.2 Дополнительные байты возможностей EC (Capability Bytes)

Для полной классификации периферии и защит используются смежные RO-регистры:

* **`0x0742` (`EC_ADDR_SUPPORT_5` / `EC_CAPS_742`)**: `BIT(4)` `FAN_TURBO_SUPPORTED`, `BIT(5)` `FAN_SUPPORT` / поддержка приоритета зарядки Type-C (`0x07CC BIT(7)`), `bits 2,3,6,7` LED vendor ([uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c), [hw.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/hw.py)).
* **`0x0765` (`EC_ADDR_SUPPORT_1`)**: `BIT(0)` Airplane, `BIT(2)` Overclock, `BIT(5)` Super Key Lock, `BIT(6)` Lightbar, `BIT(7)` Fan Boost ([uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c)).
* **`0x0766` (`EC_ADDR_SUPPORT_2`)**: `BIT(0)` Silent Mode, `BIT(1)` USB Charging, `BIT(2)` однозонная RGB-клавиатура через EC (без ITE HID — напр. MECHREVO Aurora X), `BIT(5)` China Mode / разрешение хосту задавать цвет клавиатуры, `BIT(6)` My Battery ([uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c), [Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [ec.h](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec.h)).
* **`0x07A4` (`EC_ADDR_BIOS_BYTE`)**: `BIT(7)` `LC_SUPPORT` — аппаратная поддержка СЖО (Aquaris / Oasis); `BIT(3)` `FN_LOCK_SWITCH` ([regs.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/regs.py), [profiles.h](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.h), [uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c)).
* **`0x07C8` (`EC_CAPS_7C8`)**: `BIT(5)` `LC_TABLE_SUPPORT` — EC публикует целевые значения для СЖО (`0x07E6` вентилятор, `0x07E7` помпа) и хранит выделенную таблицу вентиляторов ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [regs.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/regs.py)).

## 2. Правила дизамбигуации и классификация семейств шасси

### 2.1 Порядок приоритетов при идентификации шасси

Опора исключительно на байт `0x0740` ненадёжна из-за коллизий `ProjectID` и наличия сдвига `<< 1` на новых платах. Корректный конвейер идентификации ([profiles.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.cpp), [detect.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/detect.py), [uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c)):

1. **Приоритет шины Uniwill над Clevo**: если отвечает Uniwill EC (`INOU0000` `ECRR` и `0x0740 != 0`), классифицировать платформу как Uniwill — даже если в ACPI/WMI присутствует GUID Clevo `ABBC0F6D` (подтверждённый квирк на `MECHREVO YAOSHI X6AR55xY`, `0x1A`) ([detect.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/detect.py)).
2. **Фильтрация по `CPU vendor`** (`GenuineIntel` / `AuthenticAMD`, либо PCI `0000:00:00.0` vendor `0x8086` / `0x1022`): отсекает несовместимые профили с тем же `ProjectID` ([profiles.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.cpp), [hw.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/hw.py)).
3. **Сопоставление по DMI `board_name` (baseboard pattern)** — высший приоритет. Различает коллизии с одинаковым `0x0740`:
   * **Коллизия `0x0740 = 0x1A` (`13 << 1`)**:
     * **Intel `X6AR55xY` / `X6AR5xxY` / `X6AR5xxY_mLED`** (`IDY_7Y`, MECHREVO YAOSHI, XMG NEO 16 E25, TUXEDO Stellaris 16 Gen7 Intel): `cpuVendor = intel`, `EC 77.0` (где `0x07C6 BIT(6)` — запрос кнопки питания!), `PL4` удвоенный (`0x0727 BIT(7) = 1`), `CUME`-способный (`0x0727 BIT(6)`), `SMRW` 12-байтный.
     * **AMD `X6FR5xxY` / `X6FR57TY` / `X6FR559Y`** (MECHREVO / TUXEDO Stellaris 16 Gen7 AMD / PCSpecialist Recoil 16 AMD): `cpuVendor = amd`, `EC 112.0–117.0` / `XxFR5xxx_Pro_14.810`, `0x07C6` имеет разделяемые биты (обязателен RMW по маске `0x04`), пресет `0x07A7` = 145 W, `modePresets = ["gaming", "office"]` ([IDY_7Y.json](https://github.com/Liddo-kun/MechControl-RE/blob/main/Profiles/MECHREVO/IDY_7Y.json), [X6FR5xxY.json](https://github.com/Liddo-kun/MechControl-RE/blob/main/Profiles/MECHREVO/X6FR5xxY.json), [uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c), [architecture.md](https://github.com/Liddo-kun/MechControl-RE/blob/main/docs/architecture.md)).
   * **Коллизия `0x0740 = 0x10`**: разделяется между `GMxZGxx` (AMD, `activationAck=false`, `operatingMode=true`), `GK7NXXR` и MAIBENBEN Tsunami X629 / XMG NEO 16 E23 (Intel, проверенный профиль `uniwill-0x10`, без `CUME`) ([Platforms.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Platforms.ru.md), [uniwill-0x10.json](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/platforms/uniwill-0x10.json)).
4. **Сопоставление по `0x0740` (сначала прямое `raw`, затем сдвинутое `raw >> 1`)** + расширение `0x17`/`0x18` → `0x17xx`/`0x18xx` ([profiles.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.cpp), [hw.py](https://github.com/aspidovss/open-uniwill-cc/blob/main/uwccd/hw.py)).
5. **Динамическое обогащение из EC / `SMRW` / DSDT**: аппаратные лимиты, считанные из `SMRW` и регистров EC (`0x0727`, `0x078E`, `0x07A4`, `0x0765`/`0x0766`, `0x0456`, `0x07D2`), всегда имеют приоритет над статическими значениями в профиле ([profiles.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.cpp)).

## 4. Приоритезированный список расхождений (Punch-List) в `UCC-Revorked`

### P0 — Критические (порча регистров EC / риск для железа или неработоспособность)

1. **Неверная карта регистров `RamFan 1.5` в `crates/ucc-hardware/src/uwcc/ramfan.rs` (строки 21–35, 171–288)**
   * **Проблема:** `ramfan.rs` пишет биты `CUME|UFME|FAN_BOOST` (`0x01..0x07`) в `0x0F00` и коммит `0x01`/`0x00` в `0x0F5C`, а таблицы температур/скважности размещает в `0x0F10`/`0x0F20`/`0x0F30`/`0x0F40`. В реальном EC `0x0F00..0x0F0F` — это `CPU_UP_TEMP`, `0x0F10..0x0F1F` — `CPU_DOWN_TEMP`, `0x0F20..0x0F2F` — `CPU_DUTY`, `0x0F30..0x0F3F` — `GPU_UP_TEMP`, `0x0F40..0x0F4F` — `GPU_DOWN_TEMP`, `0x0F50..0x0F5F` — `GPU_DUTY` (с handshake `0x0F5D..0x0F5F`) ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c)).
   * **Исправление:** Переписать `ramfan.rs` на реальные 6 массивов (UpT/DownT/Duty по 16 байт, неиспользуемые ступени заполнять `0xFF`), а активацию выполнять по протоколу: `RMW 0x07C6 BIT(2) = 0` → `RMW 0x07C5 BIT(7) = 1` → запись 96 байт → `RMW 0x07C6 BIT(2) = 1` (+ `CUME`/`UFME` на `0x0727`/`0x0751`). Восстановление авто-режима — очистка `0x07C6 BIT(2)` и `0x0751` (или handshake `0x0F5D..0x0F5F`).

2. **Удаление опасных адресов `0x0753`, `0x0762`, `0x07A4`, `0x07A5` и добавление недостающих `0x0746`, `0x074E`, `0x0787`, `0x07D0`, `0x07E2..=0x07E5` в `kernel/uwcc-rs/src/validation.rs` (строки 82–112)**
   * **Проблема:** `0x0753` на современных шасси — предел тока CPU VRM; `0x0762` недокументирован; `0x074E` (реальный Fn Lock) и `0x0746` (`DB_MAX_TGP`) заблокированы и явно отвергаются юнит-тестами (`validation.rs` L259).
   * **Исправление:** Обновить `is_valid_ec_write_addr()` и юнит-тесты в соответствии с таблицами §3.1–3.5.

3. **Кодировка `PL4` (`0x0727 BIT(7)`) в `crates/ucc-hardware/src/uwcc/mod.rs` (строки 959–999)**
   * **Проблема:** `read_tdp(2)` и `set_tdp(2, watts)` всегда трактуют `0x0785` как прямые ватты `u8` (до 255 W). На платах с `0x0727 BIT(7) == 1` (`IDY_7Y` / `X6AR55xY`) регистр кодируется в полуваттах (`watts / 2`), поэтому запись 210 W задаёт **420 W**, а значения >255 W падают с ошибкой диапазона ([profiles.h](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.h), [profiles.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.cpp)).
   * **Исправление:** Читать `0x0727 BIT(7)` при инициализации (кэшировать как `pl4_doubled: bool`), масштабировать `read_tdp(2)`, `set_tdp(2)` и `SMRW[2]`/`0x07A9` на `×2` / `÷2`.

### P1 — Высокие (функциональные баги и ложная идентификация)

4. **Неверный регистр `FN_LOCK` (`0x07A4 BIT(3)` вместо `0x074E BIT(4)`) и `USB_SLEEP_CHARGING` (`0x0762` вместо `0x0767 BIT(4)`) в `crates/ucc-hardware/src/uwcc/mod.rs` (строки 221–227, 1286–1329)**
   * **Исправление:** Перевести `read_fn_lock`/`set_fn_lock` на `0x074E BIT(4)` (RMW), а `read_usb_sleep_charging`/`set_usb_sleep_charging` — на чтение статуса `0x0768 BIT(4)` (с проверкой возможности `0x0766 BIT(1)`) и импульсный триггер `0x0767 BIT(4)` (как уже реализовано для `WIN_LOCK`) ([uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c), [Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)).

5. **Неверные адреса версии EC в `kernel/uwcc-rs/src/acpi_shim.c` (строки 64–65, 1070–1072)**
   * **Проблема:** `UWCC_EC_REG_EC_VER_HI/LO` читают `0x0770`/`0x0771` (`ROMID`, часто `0xFF`/`0xFF`), а не версию EC.
   * **Исправление:** Читать `0x0454` (major) и `0x047D` (minor) ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [ec_session.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/ec_session.cpp)).

6. **Неполный протокол `cTGP`/`Dynamic Boost` (`0x0743..0x0746`) и перепутанные поля `b[4]`/`b[7]` в `decode_inou0000_12byte()` (`crates/ucc-hardware/src/uwcc/mod.rs`, строки 360–401, 553–624)**
   * **Проблема:** `decode_inou0000_12byte()` трактует `data[4]` как `base_tgp_min_w` и `data[7]` как `base_tgp_offset_w`, тогда как по `MechControl-RE` `b[7]` = базовый TGP (`DefaultTGP`), а `b[4]` = `ConfigurableTGP` (дельта) ([profiles.cpp](https://github.com/Liddo-kun/MechControl-RE/blob/main/src/profiles.cpp)). Кроме того, `set_ctgp()`/`set_dynamic_boost()` не настраивают `0x0743` (`BIT(0..2)`) и не записывают `0x0746` (`DB_MAX_TGP`).
   * **Исправление:** Исправить парсинг `b[7]` (base) и `b[4]` (cTGP delta), при записи cTGP передавать смещение `watts - base_tgp` в `0x0744`, настраивать `0x0743` через RMW и писать `0x0746`.

7. **Дизамбигуация `0x0740 = 0x1A` (Intel `X6AR55xY` vs AMD `X6FR5xxY`) и многомодельная детекция в `crates/ucc-hardware/src/uwcc/mod.rs` и `detection.rs`**
   * **Проблема:** `is_chassis_0x1a()` проверяет только `project_id == 0x1A`, смешивая Intel `X6AR55xY` и AMD `X6FR5xxY`, а `detection.rs` (L462, L511) матчит `MECHREVO` только по точному `product_sku == "0001"` и `X6FR559Y` только по `product_name` (пропуская `DMI_BOARD_NAME` `X6FR5xxY`, `X6FR57TY`, `X6AR5xxY`, `X6AR5xxY_mLED` из `uniwill-acpi.c`).
   * **Исправление:** Ввести структуру `ChassisProfile` / `EcCapabilities`, определяемую по `DMI board_name` + `CPU vendor` + `0x0740` (direct/shifted) + `0x078E BIT(6)` + `0x0727 BIT(7)` + `0x07A4 BIT(7)` + `0x0456 BIT(7)` + `0x07D2`.

### P2 — Средние (корректность краевых случаев и совместимость)

8. **Сохранение `BIT(7)` (`CHARGE_CTRL_REACHED`) при записи `0x07B9` и взаимоисключение режимов батареи (`crates/ucc-hardware/src/uwcc/mod.rs`, строки 510, 1169–1221, 1349–1362)**

   * **Исправление:** В `set_charge_thresholds()` писать `end & 0x7F` (не возвращая `BIT(7)`), и гейтить `charging_thresholds` vs `charging_profiles` по DMI-профилю платы.

9. **Отсутствие гарда `is_chassis_0x1a()` в `set_mode()` (`crates/ucc-hardware/src/uwcc/mod.rs`, строка 1092) и потолок `UWCC_PWUP_MAX_LEVEL = 3` (`validation.rs` L13, `acpi_shim.c` L322)**
   * **Проблема:** `set_mode()` позволяет записать произвольный байт в `0x0752` на `0x1A` (где `0x0752` не является индексом профиля). `PWUP` ограничен уровнем `3`, хотя EC в `0x07C7 bits 2..4` публикует уровень `4` (подтверждённый прирост +15 W на Tsunami) ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md)).
   * **Исправление:** Отклонять или перенаправлять `set_mode()` на `0x1A`; расширить `UWCC_PWUP_MAX_LEVEL` до `5` (или `4`).

10. **Чтение/запись CPU TCC Offset через `0x0786` / `0x0463` (`crates/ucc-hardware/src/uwcc/mod.rs`, строки 215, 1118–1135)**
    * **Проблема:** Константа `TCC_OFFSET_C` всё ещё указывает на `0x0743`, а методы возвращают `Unsupported`, несмотря на то что `0x0786` уже в allowlist `validation.rs`.
    * **Исправление:** Переименовать/исправить константу на `0x0786` (запись `0x80 | offset`) и `0x0463` (чтение `105 - (raw & 0x7F)`), с валидацией `0..=63` ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [IDY_7Y.json](https://github.com/Liddo-kun/MechControl-RE/blob/main/Profiles/MECHREVO/IDY_7Y.json)).

### P3 — Низкие (гигиена кода и расширяемость)

11. **Снятие `0x07C6 BIT(2)` и `0x0726`/`0x0727` при `Drop` + повторное применение после сна/смены БП**: в `UwccBackend::drop()` сейчас снимается только `0x0741 BIT(0)`, а профили батареи `0x07A6` и пороги `0x07B9` не переприменяются после подключения/отключения адаптера и выхода из suspend (EC на ряде плат сбрасывает их) ([Registers.ru.md](https://github.com/aspidovss/open-uniwill-cc/blob/main/docs/EC/Registers.ru.md), [uniwill-acpi.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c)).
